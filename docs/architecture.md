# Архитектура

Я бы начал с Python-сервиса и фоновых задач. Агенты выполняют отдельные роли внутри одного процесса обработки. Подключение к API и расчёт показателей выполняет код, анализ разговоров — LLM.

Координатор принимает запрос, фиксирует период и запускает этапы. По умолчанию это последние 30 полных дней в часовом поясе компании и предыдущие 30 дней для сравнения. Открытые проблемные сделки проверяются отдельно, в том числе созданные раньше.

CRM-агент получает через amoCRM API v4 сделки, задачи, пользователей, воронки и события: `/leads`, `/tasks`, `/users`, `/leads/pipelines`, `/events`. Использует OAuth 2.0 с обновлением токенов. Первую выгрузку дополняют webhooks и периодическая сверка через API. Изменения хранятся как история; повторные события не создают дублей.

Агент звонков получает журнал и записи через API подключённой телефонии. Конкретный коннектор выбирается после выяснения провайдера. Связь со сделкой берётся из CRM-интеграции. Если у одного контакта несколько сделок и связь не определена, звонок передаётся на проверку.

Распознавание речи формирует текст с таймкодами и разделением говорящих. Затем LLM проверяет разговор по согласованному чек-листу: потребность, возражения, причина отказа, следующий шаг. На выходе — JSON с оценками и цитатами. Неразборчивый фрагмент помечается как недостаток данных. Расшифровка не может давать системе инструкции на вызов инструментов.

Аналитик объединяет результаты. SQL считает показатели по менеджерам и источникам лидов: сделки, суммы выигранных сделок, просрочки и конверсию сопоставимых когорт. Причины отказов разделяются на указанные в CRM, озвученные клиентом и предполагаемые моделью. Для кадровых выводов одной оценки LLM недостаточно.

PostgreSQL хранит данные CRM, историю, расшифровки и анализ. Аудио хранится в S3-совместимом хранилище с ограниченным доступом и сроком хранения. Redis используется для очереди фоновых заданий. Расшифровки и результаты сохраняются вместе с ID источника и версией обработки.

Отчёт показывает, что изменилось, какие сделки требуют внимания и какие действия предлагаются. Каждый существенный вывод содержит ссылку на сделку или звонок. Вместе с отчётом возвращаются время обновления и доля обработанных записей. При сбое одного источника отчёт отмечается как неполный.

В первой версии система работает на чтение. Изменения CRM можно добавить после согласования правил и способов проверки результата.

В коде этого репозитория реализована только выборка текущих проблемных сделок. Остальные этапы описаны как проект решения.
