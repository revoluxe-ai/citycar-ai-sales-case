## 1. Архитектура решения

Я бы начал с Python-сервиса и фоновых задач. Выделил бы четыре роли:

- Координатор принимает запрос, задаёт период анализа и запускает обработку.
- CRM-агент получает сделки, задачи, пользователей и историю изменений через amoCRM API v4.
- Агент анализа звонков получает записи через API телефонии, расшифровывает и проверяет разговоры.
- Аналитик объединяет результаты и составляет отчёт для руководителя.

Для amoCRM использовал бы OAuth 2.0 и методы `/leads`, `/tasks`, `/users`, `/leads/pipelines`, `/events`. Учёл бы пагинацию, ограничения запросов и обновление токенов.

Записи звонков сначала проходят распознавание речи с разделением говорящих и таймкодами. Затем LLM проверяет разговор по согласованным критериям: выяснил ли менеджер потребность, как отработал возражения, договорился ли о следующем шаге. Выводы должны сопровождаться цитатами и ссылками на записи.

Данные CRM, расшифровки и результаты анализа хранил бы в PostgreSQL, аудио — в объектном хранилище. Для фоновой обработки использовал бы очередь на Redis.

Показатели считал бы кодом и SQL: сделки, конверсия, суммы выигранных сделок, просроченные задачи, динамика по менеджерам. LLM использовал бы для анализа разговоров и объяснения результатов.

В отчёт включил бы последние 30 полных дней, сравнение с предыдущим периодом и текущие проблемные сделки, в том числе созданные раньше. Руководитель получает выводы, список сделок, требующих внимания, и ссылки на источники.

[Подробнее об архитектуре](architecture.md).

## 2. Что выполняется автоматически и где нужен человек

Система сама собирает данные, расшифровывает звонки, рассчитывает показатели, находит проблемные сделки и готовит рекомендации.

Человек утверждает критерии оценки, проверяет спорные случаи и принимает решения по сотрудникам и клиентам. Первую версию я бы запускал только на чтение. Создание задач и изменение CRM добавлял бы после согласования правил.

Три основных риска:

- Неполные данные. Не все звонки записаны или правильно связаны со сделками. В отчёте нужно показывать, какая часть данных обработана.
- Ошибки распознавания и LLM. Спорные оценки проверяются человеком; выводы должны опираться на конкретные фрагменты разговора.
- Конфиденциальность. Нужны ограничения доступа, сроки хранения записей и согласование передачи данных внешним AI-сервисам.

## 4. Реальный AI-проект

WB SKY — мой сервис управления рекламой Wildberries. Я разработал backend, интеграции с API, обработку данных, алгоритмы управления и инфраструктуру.

В сервисе работает управление через ИИ с обменом файлами. WB SKY выгружает данные магазина, текущие управляющие настройки и инструкции по работе с ними. Этот пакет можно передать в ChatGPT или другой AI-сервис, который умеет обрабатывать такие файлы.

ИИ анализирует ситуацию и формирует управляющий Excel с предлагаемыми настройками. Файл загружается обратно в WB SKY, после чего сервис использует новые настройки в управлении рекламой через Wildberries API.

В моём рабочем сценарии анализ проходит внутри аккаунта ChatGPT. Это позволяет использовать сильные модели в рамках доступа и лимитов аккаунта, без отдельной оплаты запросов к LLM API. Обмен данными и настройками через файлы даёт возможность менять AI-сервис без переработки рекламного backend.

Стек: Python, SQLAlchemy, PostgreSQL, ClickHouse, Redis, Docker, Kubernetes, Wildberries API и Telegram Bot API.

Результат — работающий сервис, в котором решения ИИ можно передать в рекламные настройки. На собеседовании могу показать весь процесс: выгрузку, анализ в ChatGPT, управляющий Excel и обратную загрузку в сервис.

Публичный код проекта: https://github.com/revoluxe-ai/adv-bot-showcase

[Описание этого сценария](wb-sky-ai-case.md).

## 5. Чему научился за последние полгода

Углубил работу с AI-агентами в разработке. Научился лучше формализовать задачи, передавать контекст между этапами и отдельно проверять результат.

На основе OpenSpec/OPSX развивал собственный процесс работы: постановка задачи, реализация и проверка изменений. Применял его в WB Sky через Cursor и Codex, в том числе при работе в отдельных worktree.

## 6. Пример предложенного улучшения

В WB Sky я предложил связать рекламный алгоритм с выполнением плана продаж.

До выполнения плана система использует один допустимый порог стоимости заказа, после выполнения — более строгий. Я реализовал эту логику в выборе ставок и позиций.

В результате переключение режима выполняется автоматически. Пользователю больше не нужно вручную менять пороги, когда план продаж достигнут.
